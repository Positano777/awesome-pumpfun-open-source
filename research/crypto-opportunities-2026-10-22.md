# Build Crypto Tools Around Verifiable Receipts

Research checked **2026-10-22**. After the Solana trade receipt, the strongest small opportunities are **route-availability diagnostics, exchange CSV import audits, and explorer-versus-RPC data checks**. Each has concrete technical reports and a bounded implementation; none is established here as an unserved market. Existing projects already solve substantial parts of these problems, so the useful contribution is an understandable diagnostic, reproducible fixture, or upstream improvement. Stablecoin payment matching and permission provenance rank lower because demand evidence is weaker or existing software already covers much of the scope. These recommendations come from inspected issues, documentation, and license files, without running the candidate software, interviewing users, or auditing accounting/security correctness. Issue states below reflect the fetched pages on the research date.

## Route diagnostics has the clearest fresh request

**Rank 1: Route Availability Doctor — medium confidence in the problem, unvalidated adoption.** On **September 30, 2026**, a developer requested a route-aware layer in LI.FI SDK issue **#502**, open when inspected: token discovery can list an asset even when the requested chain pair and amount have no available route. The request explicitly proposes cached ROUTABLE, NO_ROUTE, and UNKNOWN states. Its existing quote-probe workaround means this is a focused improvement opportunity, rather than evidence that routing infrastructure is absent. ([Request](https://github.com/lifinance/sdk/issues/502))

The first release should accept a source chain/token, destination chain/token, amount, and optional sender context where the provider requires it. It should return a timestamped quote-check result, cache age, raw provider error category, and portable JSON report. UNKNOWN must distinguish timeouts, rate limits, unsupported requests, and unavailable provider evidence from a confirmed no-route result. The hook is simple: **“Supported token does not mean your swap has a route.”** It should request no signatures and execute no transfers.

Reuse the official LI.FI SDK or documented API instead of forking its complete execution stack. Its inspected SDK license is **Apache-2.0**; its manifest includes unit-test and typecheck scripts, but those scripts were not run in this review. A generic bridge tracker would duplicate provider functionality: official documentation already describes pending, refunded, completed, and partial outcomes. The contribution is a reproducible explanation and support report. ([SDK license](https://raw.githubusercontent.com/lifinance/sdk/main/LICENSE), [repository](https://github.com/lifinance/sdk), [status semantics](https://help.li.fi/hc/en-us/articles/10980935994779-Can-a-transfer-result-in-stuck-or-lost-funds))

Validate with three integration developers and a fixture set containing a valid quote, amount-dependent failure, stale cached result, and provider outage. Proceed after two developers use the report to resolve or clearly classify a real failure. Start offline with captured, sanitized responses; live requests need explicit provider limits and applicable API terms. Another issue, **#482**, concerns typed-data approval behavior and already has linked implementation work; that belongs in upstream reproduction/testing, not a separate product. ([Related issue](https://github.com/lifinance/sdk/issues/482))

## CSV audits complement existing accounting applications

**Rank 2: Exchange CSV Import Audit — medium confidence in recurring maintenance pain, unvalidated standalone demand.** A Crypto.com user reported ignored compound-interest rows in Rotki **#12499** on **June 30, 2026**; it was **closed/fixed**. A Binance timestamp issue in **#12143**, reported **May 5**, was also **fixed**, with timezone support shipped in v1.43.0. These support ongoing importer testing, not advertising either bug as outstanding. Ghostfolio **#7728**, open when inspected and reported **August 26**, alleges duplicate detection rejects legitimate identical transactions across accounts; its example concerns mutual funds, so it is adjacent accounting evidence rather than direct crypto demand. ([Crypto.com issue](https://github.com/rotki/rotki/issues/12499), [timezone issue](https://github.com/rotki/rotki/issues/12143), [Ghostfolio reproduction](https://github.com/ghostfolio/ghostfolio/issues/7728))

The small MVP is a local CLI for **one Crypto.com export dialect**, producing an audit and optional documented Rotki import output. Preserve original row numbers, input hash, supplied timezone, parsed timestamps, unsupported transaction types, per-account duplicate candidates, and exact-decimal asset totals. Never silently delete or repair records. “Which rows did your tracker miss?” is a stronger promise than another portfolio dashboard, provided the tool also shows rows it cannot interpret.

Prefer contributing sanitized fixtures and importer improvements to Rotki. Its inspected license is **AGPL v3**, as is Ghostfolio's; copied implementation is subject to those licenses, not automatically MIT. A separately authored companion can exchange documented formats, with dependency licenses reviewed before distribution. Rotki also has paid application features: open source does not imply every hosted feature or service is free. No tax-calculation claims are justified. ([Rotki license](https://github.com/rotki/rotki/blob/develop/LICENSE.md), [importer](https://github.com/rotki/rotki/blob/develop/rotkehlchen/data_import/importers/cryptocom.py), [Ghostfolio license](https://raw.githubusercontent.com/ghostfolio/ghostfolio/main/LICENSE), [Rotki FAQ](https://github.com/rotki/docs/blob/main/faq.md))

Validation should include daylight-saving overlaps/gaps, identical trades across accounts, mixed fee assets, quoted commas, localized decimals, and repeat imports. Ask two users to reconcile a confusing export and approve every transformed row. Keep files local; synthetic fixtures are enough for the first release. Historical-price fallback is another upstream opportunity, already proposed by a Rotki maintainer in open **#12218** on **May 14, 2026**; avoid starting a parallel price service before discussing that existing scope. ([Price proposal](https://github.com/rotki/rotki/issues/12218))

## Data health needs bounded evidence and honest coverage

**Rank 3: EVM Data Health Receipt — medium confidence in developer pain, higher implementation cost.** Blockscout **#14869**, reported **September 25, 2026**, describes missing Base blocks despite a complete-indexing status; it is **closed**, and this review did not reproduce its cause or resolution. Open **#14857**, reported **September 22**, describes token counters disagreeing with transfer endpoints and direct chain checks. These are concrete diagnostic cases, not proof every explorer instance is incomplete. ([Closed completeness incident](https://github.com/blockscout/blockscout/issues/14869), [counter discrepancy](https://github.com/blockscout/blockscout/issues/14857))

Build an original read-only client that accepts explicit RPC/explorer endpoints, chain ID, and a small block range or transaction-hash list. Compare block hashes, transaction existence, pagination boundaries, and supported receipt counts; emit timestamps, redacted endpoint identities, request counts, and unknown coverage. A successful sample is not proof that all address history is complete. Ethereum/Base fixtures are a reasonable initial scope; broad chain coverage is not supported by this research.

Avoid copying current explorer-server code casually. Blockscout master now carries **LicenseRef-Blockscout**, effective **April 22, 2026**, with custom terms. TrueBlocks core is **GPL v3** and is a possible EVM indexing/export foundation requiring further fit review. Safe transaction-service distinguishes historical code through **February 16, 2026** under MIT from newer code under **FSL-1.1-MIT**, including a competing-use restriction. These distinctions apply to the inspected components; do not generalize them to entire organizations or stacks. ([Blockscout license](https://raw.githubusercontent.com/blockscout/blockscout/master/LICENSE), [TrueBlocks license](https://github.com/TrueBlocks/trueblocks-core/blob/develop/LICENSE), [Safe service license](https://raw.githubusercontent.com/safe-global/safe-transaction-service/main/LICENSE))

Validate missing-middle-page, reorg, pruned-history, and rate-limit fixtures before live sampling. Then seek two reproducible maintainer reports. Provider access is a real constraint: archive history, traces, and request volume can cost money, and Blockscout documents paid Base PRO access. Redact API keys embedded in URLs and error payloads. ([Provider documentation](https://github.com/blockscout/docs/blob/main/base-api.mdx))

## Payment and permission reports merit smaller experiments

**Rank 4: Stablecoin Payout Receipt Matcher — low confidence in demand.** A community poster describes a customer's manual payout-intent CSV matching and duplicate incident; this is secondhand and its exact posting day was not verified. Existing **x402-recon** already publishes reconciliation/reporting commands, so “no open solution exists” would be false. Its package claims MIT and publishes source provenance, but GitHub source retrieval failed during this research; source, licensing, and runtime correctness require verification before adoption. ([Customer-proxy account](https://www.reddit.com/r/StableCoins/comments/1r27twd/reconciliation_on_stablecoin_payments/), [existing package](https://pypi.org/project/x402-recon/))

A bounded experiment is offline intent CSV plus receipt JSON for one chain and token: match exact contract, recipient, amount, and transaction/log identity; identify duplicates, unmatched rows, and ambiguity. No sending, identity inference, or tax output. Reuse the Solana receipt report format and evaluate an upstream extension before creating another repository. Validate with two payment operators and deliberately duplicated receipts; public-chain ingestion adds provider costs later.

**Rank 5: Permission Provenance Fixtures — medium confidence as an upstream contribution, low confidence as a separate product.** An **August 18–19, 2026** RevokeCash review and maintainer response disagree on approved-transfer attribution semantics. This is not a confirmed vulnerability. RevokeCash already ships approval history and trace-based attribution, with trace availability and indexing constraints; its inspected license grants MIT-style permissions. ([Review and response](https://forum.arbitrum.foundation/t/final-report-revoke-cash/31239), [license](https://github.com/RevokeCash/revoke.cash/blob/master/LICENSE))

Create synthetic fixtures distinguishing standing ERC20 allowance, Permit2 allowance, consumed one-time signature, and unknown trace evidence. Explain which evidence supports each label and seek upstream review. A consumed signature should not be presented as a standing revocable permission. Validate terminology with maintainers before investing in a UI; keep initial tests offline because multi-chain traces require infrastructure. ([Permit2 documentation](https://developers.uniswap.org/docs/protocols/permit2/overview))

The portfolio can share one strength: each tool exports a small report another person can reproduce. Finish the Solana receipt, validate Route Availability Doctor next, and send accounting or provenance fixtures upstream while testing demand. Publish another repository only when a bounded task warrants independent maintenance; a useful accepted contribution can establish more credibility than an unused fork.
